# 审查与改进记录

## v0.9.0-dev：访问安全衔接与只读体检

先修复四类问题，再增加检查入口；不改六类主菜单和旧命令含义。

1. **UFW 启用后的恢复依据缺口**：启用前保存固定配置的指纹，先以当前日志级别规范生成两个 user rules 文件，只归一化 `ENABLED` 开关。启用后的状态摘要原子写入；读取/写入失败时仍能使用此前持久化依据。配置或已保存运行摘要漂移时拒绝关闭，关闭后核对 inactive 才记恢复完成。预检要求标准 `ENABLED=no` 与有效 `LOGLEVEL`，不猜测非标准配置。参考核对 [Debian 官方 UFW 0.36.2 源码](https://deb.debian.org/debian/pool/main/u/ufw/ufw_0.36.2.orig.tar.gz) 中 `set_enabled`、`start_firewall`、`update_logging`、`_write_rules` 的关系；真实内核行为仍需 VPS 验收。
2. **未结束事务被误当成已配置**：SSH/UFW 修改及访问模块的备份/恢复在无操作判断之前检查旧事务，拒绝未确认、未回退或无法安全读取的记录。SSH/UFW 状态和 audit 显示线索，不删除标记、不执行记录内任意命令。确认旧计时器正常结束后才重新操作；旧版缺乏恢复依据的未完成记录不能补造“成功”。瞬态计时器不能保证跨重启。
3. **附属失败被吞掉**：SSH 和历史 SSH 恢复后的 Fail2ban 刷新、Hy2 请求的 UFW 放行失败，返回非零；即使失败发生在附属记录创建之前，向导仍显示部分执行并停留当前步。已成功的主操作/规则保留，分别查看记录。
4. **UFW 恢复忽略后续防护依赖**：恢复首次启用、准备关闭 UFW 时，重新检查 Fail2ban/Docker/nftables/firewalld；任何活动或未知状态均保守阻止，不自动停服务或迁移封禁动作。即便 Fail2ban 使用其他动作，也需人工处理这种组合。

新增 `audit [--json|--demo]`，显示访问、账户/公钥指纹、登录样本、端口/进程和持久化证据，独立 `security-audit` schema；旧 status schema 不变。固定命令有时间/输出限制，终端控制字符转义；缺工具、无权限、截断、抽样和未覆盖项不会显示正常。不执行文件内容，不读取私钥/环境变量，不上传报告。

补充可选 `dpkg --verify` 和限范围 ClamAV；资源与路径范围见 README。扫描先检查本地依赖/病毒库支持与可用内存；单独安装继续走已有 APT 确认/外部快照记录。扫描只生成结果，不据此批量处置。ClamAV 官方也提醒自动删除有误报风险：[扫描说明](https://docs.clamav.net/manual/Usage/Scanning.html)、[Ubuntu clamscan 参数](https://manpages.ubuntu.com/manpages/noble/man1/clamscan.1.html)。逐项加固复用原 SSH/UFW/Fail2ban 备份恢复；恶意程序隔离、自动停用陌生服务与整机重建并未实现。

自动化新增故障恢复、旧事务重入/跨模块阻止、附属失败、依赖变化、报告隐私、符号链接/FIFO、资源/输出上限、过期/缺失病毒库、命中与错误并存、中断和演示隔离。真实 ClamAV 病毒检出率、真实 VPS 的 SSH/UFW 回退和云防火墙仍不由模拟测试证明。

## v0.8.0-dev：分步初始化向导

首页新增 `I`，命令行新增 `init [--experimental|--demo]`。先选择所需步骤，再逐步检查、确认、执行、跳过或退出；执行后不自动进入下一项。六类菜单编号、原命令/JSON、原模块确认和备份/回退保持兼容；向导中 `H` 复用原有记录与恢复菜单。

审查重点是取消和部分完成的语义：许多原模块取消时也返回 0，不能据此显示成功。通过上下文观察本次持久化记录，核对主操作与附属操作分别完成，再展示命令完成；不读取配置正文，也不靠历史时间差猜测归属。未完成或无法读取记录视为待核实；明确继续需 `CONTINUE`，重复执行需 `RETRY`。中断保留记录，不自动重跑或撤销整组操作。

原 `security` 安装可能提前启动 Fail2ban，与 UFW 首次启用的保守检查冲突。向导采用独立的 UFW/nftables 与 Fail2ban/python3-systemd 固定安装动作，首次启用 UFW 排在 Fail2ban 安装/配置前；原合并入口保留。已有活动服务、其他规则或缺少依赖时仍停止，不自动关闭防护。安装/升级、3x-ui 的外部快照声明与不可完整回滚限制没有改变。

新增测试覆盖选择顺序、只读/演示、取消/部分完成、中断、记录写入失败、恢复后刷新、重进与观察隔离。源码包校验包含向导模块并在隔离目录走演示流程；一次性安装 CI 从实际安装路径验证演示入口。真实 VPS 上的 SSH/UFW、软件安装和转发仍需分步验收，自动化结果不代表这些功能已端到端通过。

## v0.7.0-dev：统一记录与受限历史恢复

本轮新增操作前持久备份/记录、历史与详情、按编号/ID 选择恢复、明确清理。记录失败阻止已接入修改；恢复使用固定模块适配器，当前状态不匹配时停止；恢复本身也保存关联记录。默认只读、逐项确认和原有失败回退继续保留。

恢复能力按模块区分：SSH 要求新定时回退和第二会话，UFW 只反向撤销安全识别的新增 allow/首次启用，Fail2ban 不恢复动态封禁；BBR/调优按保存参数，Hy2/swap 仅支持完整项目状态，时区仅恢复有效时区。APT/3x-ui/外部脚本只记录并要求必要的外部快照声明，不显示可自动完整恢复。初始化向导与整机恢复仍未实现。

存储与测试关注路径/权限/摘要、容量限制、备份失败零修改、操作后写记录失败、外部改动、并发、失败材料保留和不可恢复操作。旧版升级 CI 使用固定摘要的历史解包器与历史文件清单验证基线，再校验当前包；新增 `/var/lib/vps-script/backups` 测试标记验证程序升级保留数据。该标记只在一次性 GitHub VM 中创建，不读取真实 VPS 备份。

完整范围和状态语义见 [开发说明](DEVELOPMENT.md#现有备份与恢复覆盖)。自动化通过不能替代实际 SSH/防火墙恢复和客户端端到端验收。

## v0.6.0-dev：菜单与状态整理

在 v0.5.2-dev 审查修复基础上，把首页整理为六个任务入口：系统与软件、SSH 与安全、代理服务、网络与调优、诊断与测试、工具维护与恢复。swap/时区归入系统，Hy2 端口跳跃归入代理，BBR/内核参数归入网络，外部测试独立成诊断子菜单；首页使用 `M` 切换模式、`R` 刷新。

同时核实了“危险操作前自动备份”的现状：SSH、BBR、内核调优和工具升级已有不同范围的恢复材料，UFW 仅有首次启用事务恢复，Hy2/swap 只管理自有资源；APT/3x-ui/外部脚本没有完整回滚。维护入口展示现有能力说明，不能视为新增统一恢复工具。完整覆盖见 [开发说明](DEVELOPMENT.md#现有备份与恢复覆盖)，后续备份/历史/向导规划见 [项目计划](PLAN.md#下一阶段备份与初始化计划)。

验收重点是菜单路由、只读/演示边界、未知状态呈现、操作后回显和旧 CLI/JSON 兼容；自动测试不能替代真实 VPS 的连接、恢复和端到端验证。

## 结论

原型的模块划分、固定命令白名单、root/交互终端前置检查、文件身份校验和超时回滚方向是正确的，测试也覆盖了不少失败路径。主要问题不在“功能列表不够长”，而在**可用性闭环**：

1. 本地 v0.2.1-dev 没有提交到远端，文档中的一键地址实际 404；
2. 安装器没有升级路径，重复执行会拒绝覆盖；
3. UFW、Fail2ban、SSH 端口三者没有串起来，组合使用时互相阻塞；
4. 状态查询只有四个粗分类，执行完操作后没有对应模块的结构化状态；
5. 文档反复强调“未验证”，但缺少一份集中、可执行的下一步计划。

v0.3.0-dev 针对上述问题做了改进。提交后 GitHub Actions 在 Ubuntu 22.04 / 24.04 / 26.04（含 arm）和 Debian 12 / 13 容器中通过；一键安装与再次升级也在 Ubuntu 24.04 runner 上通过。但仍未完成真实 VPS 端到端验收。

## 仍然存在的风险

- **未在真实 VPS 验收。** 自动测试以模拟为主；SSH 第二会话、UFW 超时恢复、systemd socket、nftables 重启持久化和 Hy2 客户端跳端口都必须逐项实测。
- **UFW + Fail2ban 仍是顺序式。** 如果 Fail2ban 已经用 nftables 写入规则，UFW 预检可能保守停止；推荐顺序是先启用 UFW，再创建使用 `ufw` 动作的项目 jail。复杂既有环境仍可能拒绝自动修改。
- **SSH 只处理标准 Debian/Ubuntu 布局。** `Match`、非标准 `Include`、多因素认证、非 `/usr/sbin/sshd` 会停止；这是有意保守，不是缺陷。
- **3x-ui 只做首次安装和状态读取。** 没有自动更新、卸载、证书签发或面板端口自动放行；上游安装脚本及后续下载仍有独立信任边界。
- **Hy2 不管理云防火墙。** 服务端 NAT 规则存在不代表公网客户端可用；必须在云厂商控制台放行 UDP 范围并从外部网络测试。
- **没有 Web 面板。** 首版是 SSH 终端面板，避免额外暴露 root 级 HTTP 服务。若需要 Web，建议只绑定 `127.0.0.1`、通过 SSH 隧道访问，并单独做认证/CSRF/命令白名单设计。

## 下一阶段建议

1. **真实验收（优先）**：一台可丢弃 Ubuntu 24.04 + 一台 Debian 12，按 `docs/TESTING.md` 记录双 SSH 会话、UFW 超时、Fail2ban 封禁/解封、BBR 重启、Hy2 客户端跳端口。
2. **安全栈向导**：把“UFW -> Fail2ban -> SSH 端口”做成有顺序的检查清单，每步仍单独确认；补测已有 nftables/Docker 场景。
3. **3x-ui 生命周期**：增加更新前备份、版本检测、面板端口放行、TLS/访问验证；不自动跟随 latest。
4. **变更日志与恢复入口**：统一 `/var/lib/vps-script/` 事务记录，提供“查看最近变更/恢复”菜单。
5. **可选 Web 面板**：在 TUI 功能层稳定后，再做本地绑定 + SSH 隧道的只读/操作界面。
